# Project activity

GET /api/activity?projectId=ID returns events, hasMore, and nextBefore. Team
membership/ownership is required. Optional before loads older pages (30 per page).
New task, milestone, build, bug, and feedback creations are recorded. Updates
record changes to title/name/version/status/priority/severity/assignee/milestone,
dueDate, or reviewStatus. Description-only edits are not tracked. There is no
historical backfill, delete log, client-write endpoint, or tamper-proof audit claim.

Actors/timestamps and selected before/after values are generated by the server;
comment bodies, image bytes, secrets, and download URLs are excluded. The UI offers
refresh and older pages. The feed is not a live subscription.

Primary records and activity are separate MongoDB writes. If recording fails,
the successful primary mutation stays successful, the server logs a warning, and
X-Checkpoint-Activity: unavailable appears on its response. History may therefore
have gaps after infrastructure failures; this is an operational feed, not a
transactional compliance ledger. Indexes are created at startup.

# In-app notifications

New assignments/reassignments notify the assignee if they are a current team
member. New feedback notifies team members and the team owner. Self-notifications
are excluded and recipients are deduplicated. Events from before release are not
backfilled. Delivery is an in-app database inbox, not email, SMS, push, or realtime.

- GET /api/notifications?projectId=ID: latest 30, unreadCount, hasMore, nextBefore.
  Optional unread=true and before=ID filter the inbox and fetch older records.
- PATCH /api/notifications/:id with JSON {"read":true|false}: update read state.

Only the recipient can retrieve/update their records; current team access is also
required. The UI supports explicit refresh, read/unread, unread filtering, older
pages, and opening the related task or feedback view. Failed read-state requests
retain the prior state. Unique event/recipient indexes prevent duplicate inbox
entries for a recorded event.

Notifications are best-effort after activity recording. If their insert fails,
X-Checkpoint-Notifications: unavailable and a server warning expose the failure
while preserving the successful main mutation. There is no retry worker in this
release. Database downtime can leave notification/history gaps.
